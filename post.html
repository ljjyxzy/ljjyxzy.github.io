旅途有插曲，温柔皆圆满

  • 生活随笔
  • 旅行

九月末奔赴厦门，十月初踏秋而归。短短四天三晚的旅程，像一卷温柔轻快的小书，写满海风、烟火、自由与相遇。

同行的舍友为了省下两三百元路费，选择绿皮火车辗转南昌中转，整整二十个小时的路途，颠簸、拥挤、换乘奔波，把旅途大半松弛都耗在路上。我犹豫再三，还是选择多花一点钱，买下直达的复兴号。不求奢侈，只求安稳顺遂，让尽兴游玩后的自己，可以体面、轻松地返程。

整趟旅途原本顺遂得不像话。逛热闹的八市，访静谧的南普陀，慢走博物馆，看尽鹭岛温柔。和伙伴同行有嬉笑，独自漫游有安然，每一天都有新体验、新感悟，我以为这场旅行，会毫无缺憾地落幕。

直到返程的最后一程，一场温柔的小意外，悄悄落在旅途末尾。

动车抵达终点，夜色渐浓，将近夜里十点。我打车准备归家，接通司机电话时，便隐约觉得奇怪 —— 听筒那头的回应总是慢半拍，声音并不像是人直接说话，带着机器转译的质感。上车后我才看见，车内挂着提示牌：师傅是听障人士。

他沉默、安静，车技却格外利落，车速平稳流畅，夜色里穿梭街巷，很快就抵达目的地。

旅途即将圆满结束的那一刻，意外猝不及防地发生了。

我满心松弛准备下车拿行李，师傅却一时疏忽，忘记打开后备箱。车子轻轻提速，一溜烟开远了，只留下站在路边、空空如也的我，愣在原地。我的行李箱，随着车辆一同离去。

夜里风凉，天色暗沉，路边行人寥寥，一瞬间慌张漫上心头。我立刻反复拨打电话，可因为师傅身体的原因，通话格外艰难，接连几次拨号，才终于接通。

我着急地向他说明原委，生怕他理解偏差、怕夜色已晚、怕行李就此遗失。

电话那头没有传来师傅本人的嗓音，是他把想说的话打字输入软件，再由文字转语音，透过听筒传到我的耳朵里，语气笃定而温和：「稍等，我马上回来。」

这一段机器合成的语音，却瞬间安抚了我所有的慌乱。

我站在原地静静等待，心里不再焦灼，只剩柔软的安心。不多时，夜色深处，师傅的车缓缓折返，稳稳停在我面前。

那一刻，所有忐忑落地，所有小风波温柔收场。

这场小小的插曲，没有毁掉旅途半分美好，反而让这次厦门之行，多了一份独一无二的温柔记忆。

我也忽然懂得：很多慌乱，源于自己不够细心。若是下车前，我能提前轻声提醒师傅打开后备箱，这场小意外本不会发生。生活常常如此，一次小小的疏忽，就会带来短暂的慌张，但人间的善意，永远会兜底所有不完美。

从补码说起：我是如何真正理解原码、反码与补码的

  • 计算机组成原理
  • 数制

刚学计算机组成原理的时候，我对补码的全部认知就是一句口诀：「取反加一」。考试能过，题也能算对，但我心里一直有个疙瘩 —— 为什么偏偏是"加一"？这个 1 是从哪儿冒出来的？

直到后来把模运算和溢出放在一起推导了一遍，我才明白：补码根本不是某个人拍脑袋规定的编码方式，它是让减法变成加法之后，必然会长成的那个样子。

先忘掉编码表，想想钟表

时钟是理解这套东西最好的例子。现在是 10 点，我想让它回到 8 点，有两种办法：

  • 逆时针拨 2 小时（减 2）
  • 顺时针拨 10 小时（加 10）

两个办法结果一样。因为钟面只有 12 个刻度，12 这个量程溢出了，加 10 和减 2 在"模 12"的世界里是同一件事。这里的 12 就是模。

8 位二进制同理。它的量程是 2⁸ = 256，所以在这个世界里：

-1  等价于  255
-7  等价于  249
-128 等价于 128

所谓"负数的补码"，就是把负数翻译成这个量程里和它同余的那个正数。

"取反加一"原来只是个巧合

有了上面的铺垫，再看那个让我纠结很久的"加一"：

  7 的原码    0000 0111
取反          1111 1000
加一          1111 1001   →  这就是 -7

验算一下：
  7 + (-7) = 0000 0111 + 1111 1001
           = 1 0000 0000
           = 0 （最高位溢出，8 位寄存器只留下后 8 位）

看到了吗？之所以要"+1"，是因为按位取反得到的是 255 - 7 = 248，它是 -7 在"模 255"下的同余数；而我们要的是"模 256"下的同余数 249。两者差 1。

所以加的那个 1，补的是模的差。它从来就不是什么神秘规则。

为什么这么折腾值得

因为电路做减法很贵。如果符号位要单独判断、还要比较两个数的绝对值大小来决定谁减谁，硬件复杂度会直线上升。而一旦用上补码：

  • 符号位直接参与运算，不需要特判
  • 减法器可以彻底不要，全部走加法器
  • A - B 就变成 A + (-B)，一条通路搞定

代价是"0"只有一种表示（原码里有 +0 和 -0 两个），反而更干净了。这个取舍在工程上赚翻了。

一个我踩过的坑

补码表示的范围是不对称的。8 位补码能表示 -128 ~ 127，负数比正数多一个。我第一次写嵌入式 C 的时候，把一个 int8_t 赋成 -128 再取反，结果还是 -128，愣了半天。

原因就是：它没有对应的 +128 可以回去，取反溢出后绕回了自己。这类边界值在做定点数运算和嵌入式数值处理时特别容易咬人。

小结

回头看，我卡了那么久，是因为教材上来就丢给我"定义"，而我需要的其实是"动机"。一旦接受了"减法想变成加法"这个目标，补码的形式几乎是唯一解。

后来我养成了一个习惯：学任何编码或协议之前，先问一句"它到底在解决什么问题"。大多数看似生硬的规定，背后都有一个很朴素的工程理由。

索引不是越多越好：一次慢查询排查的复盘

  • 数据库
  • SQL
  • 性能

起因是课程设计里的一张订单表，三十万行数据。分页查询要三秒多，我的第一反应是把 WHERE 条件里出现的字段全加上索引 —— 一共加了三个。

查是快了，写入肉眼可见地变慢，导入一批测试数据从几秒涨到几十秒。这才迫使我去认真看索引到底在做什么。

先看执行计划说了什么

EXPLAIN SELECT * FROM orders
WHERE user_id = 42 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;

我盯着几个字段看：type 告诉我它用了哪种访问方式，key 是实际选中的索引，rows 是预计扫描行数，Extra 里如果蹦出 Using filesort，说明排序没能走索引。

关键发现：MySQL 一条查询通常只用 one 个索引（除非触发索引合并）。我加的三个独立索引，优化器只会挑它认为最划算的那个，另外两个在查询里基本是白占地方。

索引的代价藏在哪

B+ 树索引不是免费的午餐，它的代价至少有三处：

  • 空间：每个索引都是一棵完整的树，要单独占磁盘
  • 写入：每次 INSERT / UPDATE / DELETE 都要同步维护所有索引树，索引越多写越慢
  • 优化器的判断成本：候选索引多了，它挑错的概率也会上升

我那张表写多读少，加三个单列索引纯粹是赔本买卖。

几个真正有用的概念

回表。 二级索引的叶子节点存的是主键值，不是整行数据。如果 SELECT 的字段不在索引里，就要拿着主键再回主键树查一次，这次额外的查找就是回表。回表次数多了，甚至可能不如直接全表扫描。

覆盖索引。 如果索引里已经包含了查询需要的全部字段，就不用回表了。Extra 里出现 Using index 就表示命中了。

-- 建一个覆盖索引，把 status 和 created_at 也带上
CREATE INDEX idx_user_status_time
  ON orders(user_id, status, created_at);

最左前缀。 联合索引 (user_id, status, created_at) 相当于同时有了 (user_id)、(user_id, status) 和完整三列的检索能力。但要是单独拿 status 去查，它就用不上 —— 因为跳过了最左边那列。

我最后的改法

  1. 删掉那三个各自为政的单列索引
  2. 按实际的查询条件顺序，建一个联合索引 (user_id, status, created_at)
  3. 分页从 LIMIT offset, size 改成基于 created_at 的游标式翻页，避免深翻页时扫描并丢弃大量行

查询降到毫秒级，写入也没再拖后腿。表上的索引从 3 个变成 1 个，反而更快。

小结

这件事给我最大的教训是：索引是给"查询模式"服务的，不是给"字段"服务的。

脱离真实的 SQL 去谈"这个字段要不要加索引"，基本是在猜。现在我的顺序是：先看有哪些高频查询 → 再看它们的 WHERE / ORDER BY 组合 → 最后才设计索引。而且宁愿少加，也不凭感觉多加。

动态规划：先想清楚状态，再谈转移方程

  • 算法
  • 动态规划

有一阵子我做 DP 题的流程是这样的：读题 → 觉得眼熟 → 从脑子里翻一个模板往上套 → 套不上就看题解 → 看懂了 → 关掉题解还是写不出来。

重复了很多轮之后我意识到，问题不在模板记得不熟，而在于我跳过了最重要的一步。

被跳过的一步

DP 有两个要素：状态定义，和状态转移方程。我以前是直接冲着第二个去的 —— 因为它是写在代码里的那个部分，看起来最"实在"。但真正决定这题能不能做出来的，是第一个。

状态定义回答的是：这个数组（或这个二维数组）的每一个格子，到底代表什么。

这句话说不清楚，转移方程就只能靠背。

用最长递增子序列走一遍

经典题：给一个数组，求最长严格递增子序列的长度。

我先逼自己用一句中文把状态说清楚：

dp[i] 表示：以第 i 个元素作为结尾的最长递增子序列的长度。

注意"作为结尾"这四个字是关键。它不是"前 i 个元素里的最长"，而是"必须以 nums[i] 收尾"。加了这个约束之后，转移就变得很自然：

我要算 dp[i]，那就看前面所有位置 j。只要 nums[j] < nums[i]，我就可以把 nums[i] 接在 dp[j] 代表的那条子序列后面，长度变成 dp[j] + 1。取最大值。

dp = [1] * n                 # 每个元素至少能自成一条
for i in range(n):
    for j in range(i):
        if nums[j] < nums[i]:
            dp[i] = max(dp[i], dp[j] + 1)
return max(dp)               # 答案是全局最大，不是 dp[-1]

写出这段代码几乎没花力气，因为方程早在那一句中文定义里就写完了。

顺带一提，return max(dp) 而不是 dp[n-1]，这也是状态定义直接决定的结果 —— 最长那条不一定以最后一个元素结尾。

如果一句话说不清楚状态

这种情况我现在会当成信号：多半是维度不够，或者约束条件漏了。

比如背包问题里，"前 i 个物品、容量 j、能装的最大价值"这句话一旦完整说出来，二维数组的形状就已经确定了。如果说的时候要加"但是……""还有一种情况是……"，那通常意味着需要再加一维（常见于状态机 DP、区间 DP）。

我现在的做题顺序

  1. 先用一句中文写出状态定义，写在草稿纸上
  2. 确认边界：dp 的初始值是什么，答案是从哪儿取
  3. 推导转移：这个格子能从哪些格子来
  4. 确认遍历顺序：算 dp[i] 时，它依赖的那些格子是不是已经算过了
  5. 最后才写代码

第 4 步以前经常被我忽略，然后对着数组越界或者结果不对发呆半天。

小结

模板的价值在于帮你快速认出题目，但它替代不了思考。真正让我从"看懂题解"走到"自己写出来"的，是老老实实把状态定义讲清楚这一步。

现在我遇到卡住的 DP 题，几乎不会再急着去找递归式了，而是回到那句话上重问一遍：这个格子，到底代表什么？

把 Git 当成时间机器：从提交历史谈代码阅读

  • 编程开发
  • 工具

第一次打开一个正经的开源项目代码时，我是从上往下读的，像读课本一样。读了两天，记住的东西不到十分之一。

后来我换了个思路 —— 不再把代码当成"现在长什么样"，而是去追"它为什么变成这样"。效率完全不一样。

两个用得最多的命令

# 这个文件每一行最后是谁改的、什么时候改的
git blame -L 120,140 src/main.c

# 跟着这个文件一路走过来的全部改动（含重命名）
git log -p --follow -- src/main.c

git blame 适合 pinpoint：看到某段奇怪的代码，立刻知道是谁在什么背景下写的，还能顺藤摸瓜找到那个 commit。

git log -p 则像在看这部文件的发展史。配合 --follow 可以跨重命名追踪，不会半路断掉。

关键是看 commit 本身

真正的收获往往不在代码 diff，而在那个 commit 的提交信息和它前后的几个 commit。

一段现在看起来很绕的判断，可能当初只是为了修某个很特殊的边界 case；一个奇怪的 +1，可能对应着一次踩过坑的修复。知道了动机之后，这段代码就不再"莫名其妙"，我能判断它现在还成不成立、能不能放心删。

# 只看涉及某段逻辑的提交，还能搜 commit 信息
git log --oneline -S"retry_count"
git log --grep="fix: timeout"

几个实践习惯

  • 先 git log 再读代码。 花十分钟扫一遍提交历史，对项目脉络有个大概印象，比直接扎进文件里强得多。
  • 遇到看不懂的就 blame。 不要硬猜，直接问作者（问 Git）。
  • 善用分支比较。 git diff main..feature 能把这个特性到底改了哪些地方一次性摊开看。

反过来，对自己的提交

读了别人一堆历史之后，我对自己写 commit message 也变得更认真了。因为我知道将来会有人（大概率是我自己三个月后）用 git log 来读懂这次改动。

现在我会尽量在提交信息里写"为什么"，而不是"改了什么" —— 后者 diff 已经说清楚了，前者才是 diff 里看不到的东西。

小结

代码是一个过程的产物，不是凭空出现的文本。把它放回时间里去看，很多困惑会自动消解。

这也是我觉得 Git 最被低估的地方：它不只是版本管理工具，它是一台记录着项目全部思考过程的机器。

进程与线程：从一次上下文切换的开销聊起

  • 操作系统
  • 并发

操作系统课上讲进程切换，对我而言一直是句抽象的话："保存现场，恢复现场"。考试会写，但我脑子里没有任何量级概念。

直到有一次我试着把它的开销拆开估算了一遍，才发现"线程比进程轻量"这句被说烂的话，背后其实有一套很具体的代价模型。

切换一次到底要干什么

粗略地看，一次上下文切换的成本至少来自三处：

1. 保存和恢复寄存器

CPU 里那些通用寄存器、程序计数器、栈指针，都是当前任务的状态。切换时得先把它全部存进内核栈，回来时再填回去。这部分是纯搬运 unavoidable。

2. 地址空间的切换

这是进程切换真正贵的地方。切进程意味着要换页表（更新 CR3 之类的页表基址寄存器），随之而来的是 TLB 被打垮 —— 之前缓存的虚拟地址到物理地址的映射基本作废，新进程刚开始跑的那段时间会密集发生 TLB miss。

而线程切换共享同一个地址空间，这一步直接省掉。

3. 缓存的冷启动

CPU 各级 cache 里装的还是上一个任务的数据和指令。换人之后的一段时间内，cache miss 率会显著上升，要重新把工作集 warming up 起来。

同理，同进程内的线程切换，如果工作集接近，这部分的损失会小一些。

所以"线程轻"在哪里

把上面三点摊开，答案就很清楚了：

  • 寄存器保存 —— 两者都要
  • 页表切换 + TLB 失效 —— 只有进程切换要
  • cache 冷启动 —— 两者都有，线程间通常更轻

线程的优势不是"什么都快"，而是省掉了最贵的那一项。

一个我以前理解错的地方

我一度以为线程切换就一定便宜。后来看到资料才纠正过来：如果是跨核迁移、或者线程间工作集差异很大导致 cache 大量失效，开销也可能不低。

另外，切换本身还涉及内核态/用户态的转换、调度器的选择逻辑，这些开销和"进程还是线程"无关，是纯粹的切换代价。

对写代码的实际影响

想明白这套模型之后，我对几个常见说法有了更实在的判断：

  • "多进程更稳定" —— 因为地址空间隔离，一个崩了不拖累别的。代价是切换贵、通信要走 IPC。
  • "多线程要小心共享数据" —— 正因为共享地址空间才便宜，也正因如此才需要锁。
  • "协程很轻" —— 它连内核态都不用进，切换在用户态完成，省的就是前面第一项和内核转换的部分。

这些取舍从来不是非黑即白，而是在"隔离性、切换成本、通信成本"三者之间权衡。

小结

把一个抽象结论还原成具体的代价项，是我这学期觉得最有用的一种学习方法。

"线程更轻"不再是一句需要背的话，而是一句我能拆开讲清楚的话。这种理解在面试聊并发模型，或者真的要在线程池和多进程之间做选择时，比背十条结论都管用。

写好注释的前提，是代码本身已经足够清楚

  • 编程开发
  • 随笔

我以前写代码有个坏习惯：写完之后觉得有些地方连自己都看不懂，就在旁边补一行注释说明它干什么。当时觉得这叫"负责任"。

后来维护自己三个月前的代码时才发现，那些注释和它解释的那段烂代码一起，变成了双倍的心智负担 —— 而且很多时候注释已经和实现脱节了。

那个转折点

# 重构前
def f(a, b):
    # t 是税率，VIP 用户减免
    return a * 0.13 if b else a * 0.06

这行注释在当时是有用的，因为它弥补了 f、a、b 这些名字传递不了任何信息。但我后来意识到：注释在这里扮演的是创可贴的角色。

# 重构后
VIP_TAX_RATE = 0.06
STANDARD_TAX_RATE = 0.13

def calculate_tax(order_amount, is_vip):
    rate = VIP_TAX_RATE if is_vip else STANDARD_TAX_RATE
    return order_amount * rate

改完之后，注释一句都不需要了。而且它获得了注释给不了的好处：如果哪天改了 VIP_TAX_RATE，读代码的人不会漏掉藏在注释里的信息 —— 因为信息本身就在代码里。

我现在的判断顺序

当我"想写注释"的时候，先停一下问自己：

  1. 是不是因为我起了个坏名字？ 如果是，先改名字。
  2. 是不是这段代码做了太多事？ 如果是，先拆函数。
  3. 是不是某个魔法数字？ 如果是，提成常量。
  4. 以上都排除了，还是有必要说明 —— 那才写注释。

大部分"想写注释"的冲动，会在前两步就消解掉。

那什么情况下该写

剩下的这些，才是注释真正的主场：

  • 解释为什么，而不是做了什么。 代码能说明它做了什么，但说明不了当初为什么这么选。
  • 记录不明显的坑。 比如某个依赖库的古怪行为、某个看起来多余但不能删的判断。
  • 标明 TODO 和已知限制。
  • 给一段复杂算法指路。 写清楚思路来源或论文出处，比逐行翻译有用得多。

一个典型的好注释：

# 这里必须先 sleep 再重试：上游接口在 429 之后
# 有一小段窗口期会继续拒绝，立刻重试必失败。
time.sleep(backoff)

它解释的东西，diff 里完全看不出来。

小结

好的命名和拆分，本身就是最高性价比的文档 —— 它不会过期，也不需要维护两份。

注释的价值在于补上代码表达不了的那部分信息，而不是把代码再翻译一遍。想明白这一点之后，我写的注释变少了，但每条都更有分量。
